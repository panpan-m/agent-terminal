# Browser terminals

There are two browser surfaces, both served by `tio-server`:

| Surface | Engine | Entry |
|---|---|---|
| **Terminal** tab in the SPA | xterm.js fed by the console WebSocket (`/ws/console/{id}`) | every session, full page |
| **Full terminal** (new tab) | ttyd + `tio-web-bridge` | `session.terminal.control_url` / `view_url` |

The Terminal tab renders raw RX bytes and writes every keystroke straight to the
session (no local echo); it does not go through ttyd. ttyd still owns the full
PTY experience (resize, scrollback, terminal-side features) and never opens the
serial port:

```text
Browser (xterm.js) ─WS /ws/console──▶ tio-server ─▶ UART

Browser ─HTTP/WS─▶ ttyd ─PTY/ConPTY─▶ tio-web-bridge ─WS─▶ tio-server ─▶ UART
```

## Why the tab is not an iframe of ttyd

ttyd runs on its own loopback port and `-O` checks that the WebSocket `Origin`
matches its own host. An iframe served by `http://127.0.0.1:8765` therefore
cannot open ttyd's WebSocket on `:7682`. Proxying ttyd through the server works
functionally, but on Windows an upstream WebSocket that is torn down while the
browser disappears can leave libwebsockets with half-closed connections; after a
few such cycles ttyd stops answering `/token` and new upgrades. Direct ttyd (no
proxy) survived 40 open/close + Ctrl-C cycles in testing, so ttyd stays on its
native path and the embedded tab uses the raw console stream instead. This was
measured, not assumed; see `docs/live-debug-report.md`.

## Two entries per session

| Entry | Default port | ttyd flags | Purpose |
|---|---|---|---|
| view | 7681 | (no `-W`) | watch output |
| control | 7682 | `-W -c user:pass` | operator input, only when `control_owner=human` |

`tio-server` is the supervisor: `ttyd.enabled = true` starts both entries per
session — at boot for configured sessions and immediately when a session is
created through the API/UI. Deleting a session stops its entries; `stop_all()`
runs on shutdown so no orphan ttyd/bridge survives the service. The session API
returns `terminal.view_url` / `terminal.control_url`, which the UI turns into
**Terminal** links. Ports are picked from `view_port_base` / `control_port_base`
by finding free ports, so two sessions never collide.

The exact command it runs (also usable by hand):

```powershell
ttyd.exe -p 7682 -i 127.0.0.1 -O -m 2 -W -c operator:<pass> `
  C:\...\python.exe -m tio_web_bridge `
  --url ws://127.0.0.1:8765/ws/bridge/board-a --mode rw `
  --token-file C:\ProgramData\tio-server\bridge-token
```

Linux uses the identical argument vector with `ttyd` from `$PATH` (or
`/opt/tio-server/bin/ttyd`).

## Security

* loopback bind only (`-i 127.0.0.1`);
* `-O` checks the `Origin` header (WebSocket cross-site protection);
* control entry always has `-c` basic auth (credentials from
  `ttyd-control.pass`, generated by `init`);
* `-m` caps concurrent browsers;
* never `-a` (command injection through URL parameters);
* the bridge authenticates with `X-Bridge-Token`, not the admin cookie;
* the server still refuses writes when `control_owner=agent`, even if ttyd allows
  them (`WRITE_LOCKED` shown in the terminal as a control message).

Basic-auth is **entry level**: all browsers behind one ttyd share one identity.
For per-user identity put Caddy/Nginx with SSO in front (ttyd `-H` proxy header
mode) — the bridge still reports `source=ttyd` to the server.

## Windows / ConPTY verification (P0 gate)

Tested with the official `ttyd.win32.exe` 1.7.7 (SHA-256 verified against the
release `SHA256SUMS`) and the bundled bridge on Windows 10:

| Check | Result |
|---|---|
| ttyd serves the terminal page | pass |
| device boot banner relayed | pass (`TioSim v1.0.0 board=board-a`) |
| typed bytes reach the UART, output returns | pass (`help` → command table) |
| `Ctrl-C` forwarded as 0x03, bridge survives | pass |
| basic-auth control entry: 401 without, 200 with | pass |
| bridge survives browser disconnect | pass |

Reproduce with `python scripts/ttyd_check.py` (downloads nothing: put
`ttyd.exe` in `tools/ttyd/` first). Raw artifacts land in `artifacts/ttyd/`.

### Protocol notes (needed if you write your own client)

1. WebSocket URL is `/ws` and the client **must** request the `tty`
   subprotocol.
2. The first frame is a *binary* JSON handshake:
   `{"AuthToken": "<from GET /token>", "columns": 120, "rows": 30}`.
3. After that, frames are binary; byte 0 is the command (`'0'` = input/output
   data, `'1'` = title/command line, `'2'` = JSON window options).
4. With `-O`, the handshake must carry an `Origin` header matching the page
   origin, otherwise ttyd closes the socket during the HTTP upgrade.

## Limitations (accepted)

* terminal, not a binary viewer — use the hex view / transcript for binary;
* one PTY shared by all browsers of that entry (input interleaves; `-m` limits);
* no scrollback persistence beyond the bridge's replay of the last N bytes
  (`ttyd.replay_bytes`);
* no per-browser identity/audit (entry-level auth only);
* version upgrades can change terminal behaviour — the version is pinned in
  release packaging and checked by `tio-server doctor`.
