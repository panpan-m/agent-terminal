# Architecture

Status: implemented, verified on Windows 10 (see [VERIFICATION.md](./VERIFICATION.md)).

## 1. Process model

```text
Browser ─HTTP────▶ agent-terminal (SPA) ────────────────┐
Agent   ─HTTP────▶ /mcp ────────────────────────────┤──▶ agent-terminal ──▶ COMx / /dev/ttyUSB0
Agent   ─stdio───▶ agent-mcp ─HTTP────────────────────┘
```

| Process | Lifetime | Responsibility |
|---|---|---|
| `agent-terminal` | long-running service | sole owner of the serial port, ring buffer, MCP, admin API/SPA, WebSockets, transcripts |
| `agent-mcp` | per agent | stdio ⇄ HTTP JSON-RPC proxy; never touches the port |

Exactly one `agent-terminal` per data directory: `SingleInstanceLock`
(`platform/single_instance.py`) takes an advisory byte-range lock on
`<data-dir>/agent-terminal.lock` before uvicorn starts, so a second start exits
with code 3 instead of duplicating ownership. POSIX additionally enforces tty
exclusivity in the kernel (`flock` + `TIOCEXCL`); Windows has no equivalent, which
is why the process-level lock exists on both platforms.

## 3. Concurrency

* **One reader thread per session.** It blocks in `backend.read(4096, 100 ms)`,
  appends to the ring buffer and fans out to subscribers. It never runs a regex,
  never formats text and never blocks on a client.
* **One streaming core.** Ring append, subscriber fan-out, replay ordering and
  transcript writes live in `streaming.StreamSession`; `Session` inherits it, so
  a new transport can inherit the same concurrency behaviour instead of
  re-deriving it.
* **One writer lock per session.** `serial_command` holds it across *write +
  wait for response*, so a command cannot be interleaved. Other writers get
  `BUSY` after the timeout.
* **Subscribers use bounded queues** (`tio_server/streaming.py`). A slow browser
  drops chunks and receives an
  `overflow` notice instead of growing the process or stalling the UART.
* **Waiters** use `RingBuffer.wait_for_data`, so MCP reads block on a condition
  variable rather than polling.
* **Blocking serial work runs in worker threads** (`asyncio.to_thread`). This
  covers both the async HTTP layer *and* every MCP tool body: `_guard` off-loads
  each handler, so a 30 s `serial_read` wait cannot freeze `/api`, `/ws` or
  `/healthz`. Measured regression guard: `scripts/probe_event_loop_blocking.py`
  and `tests/unit/test_tool_offload.py`.

## 4. State and cursors

```text
rx_start ──────────────── rx_head
           buffered bytes (capacity 1–64 MiB)
```

* `cursor` is an absolute offset since session open.
* Reading never consumes; multiple readers keep independent cursors.
* If a reader's cursor fell out of the buffer, the result carries
  `gap: true` and `lost_bytes = rx_start - cursor`.
* `next_cursor` is always safe to feed back into `serial_read`.

## 5. Security model

| Surface | Authentication | Notes |
|---|---|---|
| `/` SPA, `/api/*` | loopback: local trust (Host/Origin allow-list). **Off loopback: `Authorization: Bearer <api-token>` or `?token=`** | no accounts/cookies; a Host header is not authentication, so the guard demands the token as soon as the bind leaves loopback |
| `/mcp` | `Authorization: Bearer <api-token>` | Argon2 hash in config, raw token in 0600 file |
| `/ws/console/{id}` | Origin allow-list, plus the same token gate off loopback (`?token=` for browsers) | browsers always send Origin on WS |
| `/healthz`, `/readyz` | none | minimal information |

Defaults: bind `127.0.0.1`, port allow-list, `control = "agent"` (the agent
drives the wire, the operator terminal observes), MCP has no tool to
open/close/configure a port, and every failed auth is audited.

Prompt injection: `instructions` and every tool description state that RX is
untrusted device output; no tool executes or feeds RX into a shell.

## 6. Deviations from the plan document

| Plan | Implementation | Why |
|---|---|---|
| Admin UI = FastAPI + Jinja2 + HTMX, no Node build | React 19 SPA with an **xterm.js Terminal tab** (the short-lived assistant-ui chat console was removed in v0.4), prebuilt into `web/static`; Node is build-time only | the operator wanted a real terminal, not a chat thread; the packaged server still needs no Node |
| `agent-terminal/` with `server/` subdir | repo root is the Python project (`src/tio_server`) + `frontend/` | simpler repository; process boundaries are unchanged |
| Optional `serial_expect` | implemented and enabled | cheap, read-only, useful for boot markers |
| Virtual serial adapter for `tio` CLI (P6) | not implemented | explicitly optional; out of scope for this deliverable |
| MCP spec 2026-07-28 + SDK v2 | SDK 2.3.0, Streamable HTTP, stateful transport sessions | matches the target spec; stateless tool state via `session_id` as planned |

## 7. Decisions added during implementation

* **ADR-012 — xterm.js for the operator terminal (supersedes the chat console).**
  The first implementation used assistant-ui to model commands as chat messages;
  that made interactive use (raw keys, Ctrl-C, line editing, `vim`) impossible.
  The console is now a full-page xterm.js terminal over `/ws/console`: raw RX
  bytes, keystrokes written straight to the session, cursor-resumed reconnects,
  BREAK/search/export.
* **ADR-013 — one JSON document per transcript record.** Records contain
  `data_b64` plus `len` and `offset`, so a truncated tail can be re-assembled
  without guessing encodings.
* **ADR-014 — the simulator is a first-class backend.** `sim://<name>` implements
  the same Protocol (lines, unplug/replug, shell) so the entire stack is testable
  without hardware, and the same code path serves `serial_read`/`serial_command`
  in the HIL tests.
* **ADR-015 — MCP errors carry `structuredContent`.** Tools return
  `CallToolResult(isError=true, structuredContent={"error": {...}})` so clients
  get a machine-readable `code` instead of parsing prose.
