# Architecture

Status: implemented, verified on Windows 10 (see [VERIFICATION.md](./VERIFICATION.md)).

## 1. Process model

```text
Browser ─HTTP/WS─▶ ttyd ─PTY─▶ tio-web-bridge ─WS─▶ ┐
Browser ─HTTP────▶ tio-server (SPA) ────────────────┤
Agent   ─HTTP────▶ /mcp ────────────────────────────┤──▶ tio-server ──▶ COMx / /dev/ttyUSB0
Agent   ─stdio───▶ tio-mcp ─HTTP────────────────────┘
```

| Process | Lifetime | Responsibility |
|---|---|---|
| `tio-server` | long-running service | sole owner of the serial port, ring buffer, MCP, admin API/SPA, WebSockets, transcripts |
| `tio-mcp` | per agent | stdio ⇄ HTTP JSON-RPC proxy; never touches the port |
| `tio-web-bridge` | child of ttyd | raw bytes between ttyd's PTY and the `/ws/bridge/{session}` socket |
| `ttyd` | per entry (view/control) | browser terminal, basic auth, Origin check |

## 3. Concurrency

* **One reader thread per session.** It blocks in `backend.read(4096, 100 ms)`,
  appends to the ring buffer and fans out to subscribers. It never runs a regex,
  never formats text and never blocks on a client.
* **One writer lock per session.** `serial_command` holds it across *write +
  wait for response*, so a command cannot be interleaved. Other writers get
  `BUSY` after the timeout.
* **Subscribers use bounded queues.** A slow browser drops chunks and receives
  an `overflow` notice instead of stalling the UART.
* **Waiters** use `RingBuffer.wait_for_data`, so MCP reads block on a condition
  variable rather than polling.
* **Blocking serial work runs in worker threads** (`asyncio.to_thread`) from the
  async HTTP layer; the event loop never blocks on a UART.

## 4. State and cursors

```text
rx_start ──────────────── rx_head
           buffered bytes (capacity 1–64 MiB)
```

* `cursor` is an absolute offset since session open.
* Reading never consumes; multiple readers keep independent cursors.
* If a reader's cursor fell out of the buffer, the result carries
  `gap: true` and `lost_bytes = rx_start - cursor`.
* `next_cursor` is always safe to feed back into `serial_read`.

## 5. Security model

| Surface | Authentication | Notes |
|---|---|---|
| `/` SPA, `/api/*` | HttpOnly signed cookie + CSRF header | Origin checked on writes |
| `/mcp` | `Authorization: Bearer <api-token>` | Argon2 hash in config, raw token in 0600 file |
| `/ws/console/{id}` | admin cookie | Origin checked |
| `/ws/bridge/{id}` | `X-Bridge-Token` | separate token, never the admin cookie |
| ttyd | basic auth (`-c`) or proxy header | entry-level only, by design |
| `/healthz`, `/readyz` | none | minimal information |

Defaults: bind `127.0.0.1`, port allow-list, `control_owner = human`, MCP has no
tool to open/close/configure a port, and every failed auth is audited.

Prompt injection: `instructions` and every tool description state that RX is
untrusted device output; no tool executes or feeds RX into a shell.

## 6. Deviations from the plan document

| Plan | Implementation | Why |
|---|---|---|
| Admin UI = FastAPI + Jinja2 + HTMX, no Node build | React 19 SPA using **assistant-ui** primitives, prebuilt into `web/static`; Node is build-time only | explicit product requirement to use assistant-ui components; the packaged server still needs no Node |
| `tio-suite/` with `server/` subdir | repo root is the Python project (`src/tio_server`) + `frontend/` | simpler repository; process boundaries are unchanged |
| ttyd 1.7.7 "P0 go/no-go" | verified on Windows ConPTY: banner, keystrokes, Ctrl-C, basic auth (see VERIFICATION) | gate passed |
| Optional `serial_expect` | implemented and enabled | cheap, read-only, useful for boot markers |
| Virtual serial adapter for `tio` CLI (P6) | not implemented | explicitly optional; out of scope for this deliverable |
| MCP spec 2026-07-28 + SDK v2 | SDK 2.3.0, Streamable HTTP, stateful transport sessions | matches the target spec; stateless tool state via `session_id` as planned |

## 7. Decisions added during implementation

* **ADR-012 — assistant-ui for the operator console.** The console is a chat
  thread: an operator message becomes a CR-terminated command, the response is an
  assistant message, unsolicited output stays in the live RX pane. assistant-ui
  provides the thread/composer/message primitives; the advisory "hand control to
  the agent" state is enforced server-side, not in the UI.
* **ADR-013 — one JSON document per transcript record.** Records contain
  `data_b64` plus `len` and `offset`, so a truncated tail can be re-assembled
  without guessing encodings.
* **ADR-014 — the simulator is a first-class backend.** `sim://<name>` implements
  the same Protocol (lines, unplug/replug, shell) so the entire stack is testable
  without hardware, and the same code path serves `serial_read`/`serial_command`
  in the HIL tests.
* **ADR-015 — MCP errors carry `structuredContent`.** Tools return
  `CallToolResult(isError=true, structuredContent={"error": {...}})` so clients
  get a machine-readable `code` instead of parsing prose.
